# Bounded deletion cost profile

The Debug admin verb **GC Deletion Costs** reads a snapshot of the running garbage process. It does not run collection, delete objects, find references, reset counters or write logs. The snapshot copies its rows, so callers cannot mutate the retained counters through it.

`deletion_profile` keeps the first 128 observed type names and one `(other types)` aggregate for later types. Keys are strings; rows contain numbers only. `profile_row(type_name)` is the bounded internal accessor, and `profile_snapshot()` returns copies. There are no target references, ref IDs, per-event details, world scans or sorting on the deletion path. Existing `logging` remains the legacy forced-queue counter and is not a collection-failure classification.

Each row records `cleanup_count`, `cleanup_total_ds`, `cleanup_max_ds`, `cleanup_yielded` and corresponding `forced_*` values. Cleanup measures completed `Destroy()` calls made by `qdel()`, including a returned let-live hint and cleanup that deletes its own target. Recursive/repeated calls rejected by the existing deletion guard do not count again. Forced measures completed collector `del()` calls and the immediate hard-delete hint. Collection by BYOND reference counting, direct engine `del()` elsewhere, native finalizers, pool eviction and pre-process startup cleanup are outside this profile. Counts do not establish collection success or failure.

Timing uses `world.timeofday`, in **deciseconds** (10 ds = 1 second), with one midnight wrap handled. It is coarse elapsed wall time, not CPU time: waits and scheduler delays are included, short operations can measure zero, nested cleanup costs overlap, and totals across phases/types must not be treated as exclusive process time. Calls lasting a full day or clock adjustments cannot be measured reliably. `*_yielded` means `world.time` changed during the call; it is not proof of an explicit sleep. Calls that abort through an uncaught runtime error do not produce a completed timing sample.

Normal work adds two wall-clock reads, two game-clock reads, a captured type string and a bounded row update per measured operation. No tracing is automatically enabled and no performance improvement is claimed. The profile lasts for the garbage process's lifetime; restarting/replacing that process resets it. There is no live reset or toggle in the diagnostic UI.

The design was informed by the separate Destroy/hard-delete counters in [Baystation12 at ca90ce8](https://github.com/Baystation12/Baystation12/blob/ca90ce8b501c4e04f24c1510990fc6f86623d4f1/code/controllers/subsystems/garbage.dm), adapted to Civ13's existing legacy ordering and budgets rather than importing its subsystem.

Run `tests/garbage_profile/run.py --byond-bin <516.1681-bin>` with a verified Python interpreter. `--negative-control bound`, `cleanup`, `forced` and `clock` alter generated source only and must detect the intended defect. The fixture compiles the production GC/helper with existing isolated adapters, exercises recursive and self-deleting cleanup, queued/immediate deletion, let-live, real yielding cleanup, totals/maxima, midnight wrap, row bounds and snapshot isolation, then repeats the existing 300-candidate/30-forced collector regressions. A 10,000-update microbenchmark reports coarse isolated wall time, not whole-game profiling overhead. It does not start the game or prove production latency, long-term memory behavior or graphical admin acceptance. Its new suite has its own CI guard; existing broad suites remain opt-in.
